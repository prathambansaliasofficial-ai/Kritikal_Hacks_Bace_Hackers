# Team workflow — branches, ownership, handoff

Read this once before touching code. It exists so four people can work in parallel
without breaking each other or inventing their own API shapes.

## 1. Who works where

| Person | Branch | Owns | Never edits |
|---|---|---|---|
| Lead / integrator | `main` (merge only) | `C0`, `T8.2`, final integration, progress header | module internals unless fixing a merge |
| Backend dev | `backend/<name>` | `backend/`, root `Makefile`, root `SETUP.md` (only when the task says so) | `frontend/`, `middleware/` |
| Middleware dev | `middleware/<name>` | `middleware/` | `frontend/`, `backend/` |
| AI / TinyFish dev | `ai/<name>` | `middleware/src/tinyfish/**`, TinyFish prompts, `middleware/scripts/smoke-tinyfish.ts` | escrow, Fastify routes, backend, frontend |
| Frontend dev | `frontend/<name>` | `frontend/` | `backend/`, `middleware/` |

One person = one branch. Do not put two modules on one branch. Do not push to `main`.
`main` is the integration branch and must always be demo-ready.

> If the same person owns two modules, use two branches and two PRs. This keeps review
> and rollback simple.

## 2. First-time setup

Wait until the lead has pushed baseline commit `C0`. Then:

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c backend/<your-name>     # or middleware/<name>, ai/<name>, frontend/<name>
```

Read in this order, and stop after the files listed for your task:

1. Your module `AGENTS.md` (`frontend/`, `backend/`, or `middleware/`).
2. Your module `SETUP.md`.
3. Your task block in `whole_plan.md`.
4. `docs/task-ownership.md`.
5. The context pack for your batch (`docs/context/C*.md`).
6. Only the code files listed in that pack.

Do **not** read the whole repo to "get context". If a task needs an unlisted file,
stop and ask the lead.

## 3. The daily loop

```bash
# 1. start from latest integration branch
git fetch origin
git rebase origin/main

# 2. pick the next task assigned to YOUR module in docs/task-ownership.md
# 3. read only that task's context pack and listed files
# 4. implement code + tests/docs required by the task
# 5. run the module checks from your AGENTS.md
# 6. update your module log and your task marker in whole_plan.md
# 7. refresh generated module copies
npm run sync:docs
npm run check:docs

# 8. commit only your module + the exact root files the task allows
git add backend/ whole_plan.md            # example: backend branch
git commit -m "feat(api): expose parcels, alu grid and bundles"
git push -u origin backend/<your-name>
```

Open a PR into `main`. The lead merges in dependency order (see §5).

## 4. Root-file conflict rules (important)

Several branches edit `whole_plan.md`. Keep it conflict-free:

| File | Who edits | Rule |
|---|---|---|
| `whole_plan.md` task markers | each module owner | change only your own task headings `[]` → `[.]` |
| `whole_plan.md` progress line / phase counters | lead | interns do not edit |
| module log (`*/log-*.md`) | that module owner | append only; do not rewrite history |
| `docs/api-contract.md`, `docs/decisions.md`, `docs/checks.md` | lead + affected owners | change only in the same PR that changes the code |
| module copies (`frontend/whole_plan.md`, `*/docs/**`) | nobody | generated by `npm run sync:docs`; never edit by hand |
| module `AGENTS.md`, `SETUP.md` | that module owner | update when commands or scope change |

If `whole_plan.md` conflicts, keep **both** task-marker changes and re-run
`npm run sync:docs`. The lead fixes the progress header and phase counters.

## 5. Merge order

Merge in this order. Later modules may build against the documented contract before
the dependency is merged, but the real demo only works after this order:

1. `C0` baseline (lead).
2. Backend `B1` → `B2` (database + parcel/ALU/bundle).
3. Middleware `M1` (TinyFish proof, escrow status, deploy artifact) in parallel with `B1`.
4. Backend `B3` → `B4` → `B5` (evidence, identity, orders, checks, settlement).
5. Middleware `M2` (chain smoke, Sepolia, multi-portal) in parallel with `B3`–`B5`.
6. Frontend `F1` → `F2` → `F3` (map, review, wallet, buy, polish).
7. Lead `T8.2` demo runner, then `T8.3-D` final docs/hardening.
8. Stretch only if time: backend `B6`, middleware `M3`, frontend `T9.3-F`.

If a frontend or backend task needs an endpoint that is not merged yet, use the exact
shape in `docs/api-contract.md` and mock it in tests. Never invent a new field.

## 6. Handoff contract

The shared contract is fixed in `docs/api-contract.md` and `docs/decisions.md`.
To change it:

1. Update the root contract/decision first.
2. Update the code and tests in the same PR.
3. Run `npm run sync:docs` so every module copy matches.
4. Tell the affected owner in the PR description.

What each owner hands over:

- **Backend** → live endpoints + tests + example `curl` output in the log.
- **Middleware** → endpoint shape + real TxHash/runId proof + `.env.example` keys.
- **AI** → prompt file, sample real run output (no key), and the fields it can/can't fill.
- **Frontend** → screens that call only the documented endpoints, with loading/error/empty states.

## 7. Definition of done (all modules)

A task is done only when all are true:

- [ ] Code matches the task block and the API contract.
- [ ] Tests named in the task pass; module typecheck/lint/build passes.
- [ ] No secret, fake key, fake run ID, fake TxHash, or invented government record.
- [ ] Demo data carries `DEMO_FIXTURE_NOT_OFFICIAL` (or API `demo: true`).
- [ ] Module log updated with date/time/session and the exact commands run.
- [ ] Your task marker in `whole_plan.md` is `[.]`.
- [ ] `npm run sync:docs && npm run check:docs` pass.
- [ ] Commit message matches the batch message in `whole_plan.md`.

## 8. Stop conditions (do not guess)

Stop immediately and write `**BLOCKED:**` in the task block + module log if:

- a required env key is missing (`TINYFISH_API_KEY`, Sepolia key/RPC),
- the task needs a file or endpoint not listed in your context pack,
- the API contract does not describe the shape you need,
- a test needs a real government record you do not have,
- you are about to edit another module.

Ask the lead with: task ID, what you tried, the exact error, and the smallest thing
you need. A blocked task stays `[]`; never fake progress.

## 9. Secrets and safety

- `.env` files are local only and must never be staged.
- Only Hardhat account #0 dev key may appear in docs as an example.
- No mainnet, no real money, no legal title transfer.
- Never claim demo data is official government data.

## 10. Review loop (process + template + archive)

**Session** = ek AI run ek module mein. Har session is exact order mein chale:

**(a) RESOLVE** — Pichle session ke open review comments theek karo. Har comment ke liye fix commit hash likho aur `Status: RESOLVED` set karo. `[BLOCKER]` comments pehle resolve hone chahiye, tabhi step (c) start ho.

**(b) REVIEW** — Pichle session ka kaam review karo. Code par **READ-ONLY**: reviewer sirf apni module ki review file edit karega, source code nahi. Reviewer asli `git diff <range>` padhegi unreviewed commit range ki, author's log nahi. Reviewer typecheck/build/tests chala sakti hai (source mein koi edit nahi).

**(c) WORK** — Plan ka aagla task(karo).

**(d) LOG** — Apne module log (`log-f/b/m.md`) update karo aaj ki date/time/session ke saath.

### Review entry template (har module ki review file mein header mein ye format rakhein)

```
## R-<n> — reviewing <author-session-id> (commit <abc123>..<def456>) — by <reviewer-session-id>
Checked: <kya actually kiya gaya: diff read, typecheck/build/tests aur result, kaunsa api-contract.md section compare kiya>
- [BLOCKER|MAJOR|NIT] <file>:<line> — <problem + why>. Expected: <contract/rule>
Verdict: CHANGES_REQUESTED | APPROVED
Status: OPEN | RESOLVED (fixed in <hash>)
```

Review file ke top par ye pointer rakhein: `Last reviewed commit: <hash>`.

### Review rules

1. Evidence, not logs: reviewer `git diff` / commit range padhti hai.
2. "No mistakes" sirf proof ke saath allowed hai. Har review mein `Checked:` line honi chahiye. Bina `Checked:` wali review invalid hai.
3. Har comment par severity: `[BLOCKER]` / `[MAJOR]` / `[NIT]`. Open `[BLOCKER]` = naya task start nahi. Verdict: `APPROVED` ya `CHANGES_REQUESTED`.
4. Kram `(a) → (b) → (c) → (d)` ka palan ho, taaki ek-session ki deri na ho.
5. Review files module ke andar: `frontend/review-f.md`, `backend/review-b.md`, `middleware/review-m.md`. Archive rule: jo entry `RESOLVED`/`APPROVED` ho aur pichle 5 entries se purani ho, use `<module>/archive/review-<x>-YYYY-MM.md` mein move karo taaki AI context chhota rahe. Archive files default mein nahi padhi jati.

### Worked example

Session 1 (middleware) commit `abc123` mein `GET /escrow/status` add karta hai. Session 2 (middleware reviewer) entry likhti hai:

```
## R-1 — reviewing session-M1 (commit abc123..def456) — by session-M2
Checked: git diff abc123..def456 pada; `npm --prefix middleware run typecheck` pass; `npm --prefix middleware test` 7 passing; `docs/api-contract.md` §4 `{orderId,state,label}` match kiya.
- [NIT] middleware/src/server.ts:45 — error body key "error" hai par message mein full stop nahi; contract `{"error": string}` match karta hai, thik hai.
Verdict: APPROVED
Status: RESOLVED
```

### Review fix commit exception

Rule 2 (3 tasks ke baad commit) ka apvaad review comment fixes ke liye allowed hai: `fix(scope): resolve R-<n>` message use karein taaki fix commit hash review entry mein record ho sake.

## 11. Cross-module needs (explicit sync)

Kyunki modules real-time sync nahi karte, har module log mein `## NEEDS FROM OTHER MODULE` section jodhein. Format pr line:

`- [] needs: <target module> | what: <endpoint/field/behaviour> | contract ref: <§> | requested by: <session>`

Delivery hone par `[.]` karo. `npm run sync:docs` inko `<module>/docs/cross-module-needs.md` mein collect karega taaki har module apne docs mein doosre module ki demands dekh sake (root nahi padhna padega). `docs/api-contract.md` sirf source of truth rahegi shapes ke liye; contract-change wala need lead se approve karna hoga.
